### 1. 第八章收尾：需求工程七个动作与验证管理（00:00—27:50）

课堂先快速回顾了上节课的需求工程前 3 步（**启动 Inception → 获取 Elicitation → 细化 Elaboration**），随后重点展开后 4 步，形成完整闭环：

| 阶段 | 核心动作 | 通俗理解与产出 |
|---|---|---|
| **1–3. 前三步回顾** | 启动 → 获取 → 细化 | 从“1–2 页客户简述”抠出对象/服务/约束，产出**《需求规约草稿》**（文字+用例图），再通过功能/类/行为三维建模产出**《需求分析规约草稿》** |
| **4. 协商 (Negotiation)** | 识别关键干系人 → 确认可行性 → 达成双赢 | 客户想要的往往超出预算或工期。双方就功能/非功能需求的优先级谈判，达成 **Win-Win（双赢条件）**——明确“这期做什么、砍掉什么” |
| **5. 规约 (Specification)** | 修订并定稿两份正式文档 | 根据协商结果调整草稿，正式定稿**《需求规约》**与**《需求分析规约》**（可以是文档、图形模型、数学模型、场景集或原型） |
| **6. 验证 (Validation)** | 静态测试 / **FTR 同行评审** | 相当于对需求文档做“质检”：检查**有无歧义、前后矛盾、遗漏、错误**，以及是否符合过程与产品标准 |
| **7. 管理 (Management)** | **SCM（软件配置管理）** | 需求定稿后放入配置库（如 Git/GitHub）。后续需求要改时，执行 `Check-out → 修改 → Check-in` 形成新版本并追踪变更影响 |

#### 1.1 需求验证（§8.6）：怎么给需求文档做“质检”？

验证的本质是对《需求规约》和《需求分析规约》做**静态测试（Review）**，工程上通常采用 **FTR（Formal Technical Review，正式技术评审）**——由同行组成的评审小组（含主持人 Moderator、朗读者 Reader、记录员 Recorder 等）逐条检查以下核心问题：
1. **目标一致性：** 每条需求是否都符合项目总体目标？有没有遗漏非功能需求（NFR）？
2. **抽象层次是否恰当：** 需求阶段是否过早写进了不该有的技术细节（如 SQL 怎么写、用什么框架）？
3. **无歧义与可追溯：** 需求边界是否清晰？每条需求能否追溯到提出它的利益相关者（Attribution）？
4. **可实现性与可测试性：** 需求与运行/宿主环境（Host）是否冲突？做出来后能不能测？
5. **模型划分与模式复用：** 用例功能是否独立（比如别把“事件处理”和“远程看家”硬塞进同一个用例里）？是否恰当复用了已验证的需求模式？

### 2. 第九章导入：需求分析目标与经验规则（27:50—45:20）

#### 2.1 需求分析的四类视图与三大总体目标

老师指出英文教材第 9–11 章的编排结构略有交叉，课堂按**“场景建模（用例图）→ 功能建模（活动图/泳道图）→ 基于类的建模（类图）→ 行为建模（状态图/时序图）”**的主线来学（其中流模型/数据流图等传统方法如今已较少使用）。

构建需求分析模型有 **3 个总体目标（§9.1.1）**：
1. **描述客户需要什么：** 从不同视角抽象问题，消除理解偏差。
2. **为软件设计奠定基础：** 《需求规约》和《需求分析规约》是后续**概要设计（架构设计）**与**详细设计（组件设计）**的直接依据。
3. **提供可验证的依据：** 形成一套在软件建成后可用于系统测试和验收测试的明确基准。

#### 2.2 必须牢记的分析经验规则（§9.1.2 Rules of Thumb）

1. **聚焦业务问题域，保持高抽象层次：**
   - **【课堂反复强调的红线】** 在需求工程（《需求规约》与《需求分析规约》）中，**绝对不能涉及具体开发技术**——不要写选 Java 还是 C++、选 MySQL 还是 Redis、用什么 IDE 或服务器部署环境！那些是设计/实现阶段的事，需求阶段只谈业务本身。
2. **每个元素都要增进整体理解：** 模型中的图和文字要从信息、功能、行为三个维度互相印证，不能画蛇添足。
3. **推迟基础设施与部分非功能细节到设计阶段**（例如安全加密算法选型、负载均衡架构等）。
4. **最小化系统耦合（Low Coupling）：** 在分析类之间的协作交互中，接口传递的参数数量要尽量少、数据结构尽量简单，保持低耦合。
5. **确保模型为所有利益相关者创造价值，并尽量保持简单（敏捷原则）。**

#### 3.1 什么是领域分析？为什么它是“每年必考”的核心思想？

很多小软件公司天天“救火”，做一个新项目就从零写一套代码；而成熟的中大型软件企业（比如专做视觉瑕疵检测、专做高校财务系统的公司），会把**同一个行业/领域的多个相似项目**沉淀下来，提炼出**可复用的分析类、设计类和分析模式**，形成公司自己的**标准业务类库**（就像 Java 自带标准类库一样）。

- **过程定位：** 领域分析不是只针对某一个项目，而是一个贯穿多个项目的**普适性/伞状活动（Umbrella Activity）**——做完第 1 个图像检测项目后，把“灰度处理、边缘检测、瑕疵识别、报表”等类重构泛化；做到第 2、3 个项目时直接复用并扩充属性（如把 16 位升级为 64 位），开发成本能从 200 万降到 50 万！

#### 3.2 领域分析的输入与输出流程

```text
[ 四大知识来源 ]                    [ 领域分析过程 ]                      [ 复用产出 ]
1. 技术文献 (如图像处理论文)  ──┐
2. 已有应用 (同类历史项目)    ──┼──>  提取名词/分类 + 制定复用标准  ──>  标准分析类库 (UML 类图)
3. 客户调研 (Customer Survey) ──┤     (类属性/方法泛化、定义规范)         & 领域分析模式
4. 专家建议与未来趋势 (如 AI) ──┘
```

### 4. 场景建模：用例图与四种关系（73:10—94:55）

**§9.2 场景建模（Scenario-Based Modeling）** 的核心工具是 **UML 用例图（Use Case Diagram）**，它从“用户/外部视角”描述系统能提供哪些功能。

#### 4.1 画用例图的三条硬性实战规则

1. **参与者（Actor）≠ 自然人（User）：**
   - Actor 代表的是**系统外部的“角色”**（可以是人，也可以是外部系统或硬件如 `Sensor` 传感器）。
   - **例子：** 家里只有你一个人用 SafeHome 安防系统，但你在系统里既当“普通房主（布防/撤防/看监控）”，又当“系统管理员（配密码/加传感器）”。在用例图里，必须拆成 **`Homeowner`** 和 **`Administrator`** 两个不同的 Actor，因为权限和职责不同！
2. **用例（Use Case）必须具有“功能独立性”且“粒度适中”：**
   - 不能把“配置系统 + 报警处理 + 远程看家”全塞进一个大用例里。
   - **【老师经验法则】** 一个健康的用例，在后续提取名词时**至少应能提取出 $>1$ 个业务分析类**。如果一个用例只对应 1 个孤零零的类甚至没有实体类，说明它粒度太细，应该和其他相关用例合并。
3. **用子系统（Package）组织复杂用例图：**
   - 当系统较大时（如往届“旅途印记”项目或图书借还系统），应按模块划分子系统包（如“用户管理子系统”、“行程规划子系统”、“预算统计子系统”），避免几十个椭圆和线条挤成一团。

#### 4.2 用例图中的核心关系（重点区分 `include` 与 `extend`）

| 关系名称 | 箭头表示 | 通俗含义与课堂例子 |
|---|---|---|
| **关联 (Association)** | 实线（单向或双向箭头） | 表示 Actor 与 Use Case 之间的交互（如用户查询行程，既有输入又有反馈，可用双向关联） |
| **泛化 (Generalization)** | 实线 + 空心三角箭头（指向父类） | 即“继承”关系。如 Actor 中的 `本科生`、`硕士生`、`博士生` 泛化自父类 `学生`；用例之间也可有泛化，是后续**类继承**的重要依据 |
| **包含 (`<<include>>`)** | 虚线箭头（指向被包含的公共/子用例） | **“必然执行 / 子功能拆分”**：例如`用户管理`必然包含`登录账号`和`个人信息管理`（也可用来表达子系统包含哪些功能） |
| **扩展 (`<<extend>>`)** | 虚线箭头（从扩展用例指向基础用例） | **“条件触发 / 调用特定方法（Operation）”**：基础用例平时正常跑，**只有满足特定条件时才触发**扩展用例！<br>**课堂例子：** 电商`买电器`用例，平时直接结账；只有**“满 1000 元”**时才触发`满 1000 送 100` 扩展用例（对应触发某个类或外部促销类的计算方法，这也是双 11 频繁上线新促销活动而不改主流程的架构秘诀） |

*(注：课堂同时提及类图中常见的**依赖关系**——虚线箭头，如“课程表类”依赖“课程类”。)*

### 5. 用例脚本与功能建模：活动图 & 泳道图（119:40—145:40）

#### 5.1 用例脚本（Use Case Script）：把椭圆写成文字剧本

光画一个叫“登录系统”或“借阅图书”的椭圆是不够的，每个用例都必须配一份**用例脚本**，包含 6 项标准要素：
1. **用例名称** & **参与者（Actor）**
2. **前置条件（Precondition）：** 执行该用例前必须满足的状态（如`图书借阅`前，读者和管理员必须均已登录）。
3. **后置条件（Postcondition）：** 用例执行完后系统状态的变化（如成功生成一条借阅记录；若失败则系统保持未启动/未借出状态）。
4. **基本事件流（Basic Flow）：** 一切顺利时的标准步骤（用户输入用户名密码 → 系统查库比对 → 校验通过 → 登录成功）。
5. **分支事件流（Alternative Flow）：** 正常业务下的不同选择分支（如密码输错后重新输入并最终成功，回到基本流）。
6. **异常事件流（Exception Flow）：** 发生错误或异常时的处理路径（如用户名不存在、连续输错 3 次密码锁定退出）。

*(课堂同时指出了教材 SafeHome 用例图的一处瑕疵：例如远程监控中心等交互需补全，不能漏掉调用链。)*

#### 5.2 功能建模：从用例脚本 → 活动图 → 泳道图（Swimlane）

拿到每个用例的脚本后，如何进行**功能建模**？

```text
[ 用例图 + 用例脚本 ]  ──(画单个用例的内部流程)──>  [ 活动图 Activity Diagram ]
                                                            │
                                            (按参与协作的“类”切分泳道)
                                                            ▼
                                              [ 泳道图 Swimlane Diagram ]  <──(与类图反复迭代校验)
```

1. **活动图（Activity Diagram）：** 相当于一个用例的**详细流程图**。课堂以 SafeHome 的 `Access Camera（远程查看摄像头）` 为例：输入密码（错 3 次直接退出）→ 验证通过后选择菜单功能（按特定摄像头图标或下拉菜单选摄像头）→ 查看视频流并移动视角 → 判断是否继续查看。
2. **泳道图（Swimlane Diagram）：** 把活动图按“谁来干这步”竖向切分成几条泳道！
   - **关键转换：** 在分析阶段，泳道的表头不是人，而是**参与完成这个用例的“分析类”**！例如 `Access Camera` 用例拆出三个类：`Homeowner`（房主）、`Camera`（摄像头）、`Interface`（接口控制类，类似 Java Web 开发中的 `Controller`，负责承上启下协调前后端）。
   - **迭代校验价值：** 画完泳道图后，如果发现某个类在泳道里几乎没干活、或者两个类职责重叠，就可以反馈回去**合并或拆分分析类**，反复迭代让类图和接口定义更合理。

### 6. 第十章导入：基于类的建模——识别分析类（145:40—164:50）

**第十章（Class-Based Methods）** 是整个面向对象需求分析的**重中之重**（老师举例：有项目组花 25 天把分析类图改了六七遍，一旦类图定稳了，后面写代码和改需求会非常快）。

#### 6.1 语法分析法（Grammatical Parse）：问题空间 vs 解空间

如何从《需求规约》和每个用例脚本里把类找出来？
1. **扫出所有名词/名词词组**填入候选表（注意合并同义词），作为**潜在分析类（Potential Analysis Classes）**；**扫出实意动词**作为候选方法（归属于某个名词的方法，如“拨打电话”）。
2. **区分“问题空间”与“解空间”：**
   - **解空间（Solution Space）：** 实现软件解决方案**真正需要处理和存储数据**的名词/动词（如 `Sensor` 有传感器 ID、类型、报警阈值需要记录和设置，属于分析类）。
   - **问题空间（Problem Space）：** 仅用来描述业务背景、系统**不需要存储其数据或不需要实现**的名词/动词（例如“由安装工人负责安装”，如果系统不需要记录安装工人的姓名、电话和安装记录，那么“安装工人”就不作为系统内的分析类）。

#### 6.2 分析类的 7 种典型表现形式

筛选候选名词时，真正的分析类（Analysis Class）通常属于以下 **7 类**之一：

| 类别 | 说明与课堂例子 |
|---|---|
| **1. 外部实体 (External Entities)** | 与系统交互并产生/消费信息的其他系统、设备或人（如 `Sensor`、`支付宝`）。*注：若外部系统只提供接口、无需在本系统存数据，则不建成本地分析类* |
| **2. 事物 (Things)** | 问题信息域中的报告、显示、信件、信号等（如报表、弹窗显示结果、报警信号） |
| **3. 事件/发生 (Occurrences / Events)** | 系统运行上下文中发生的关键事件（如 `Alarm` 报警事件——需记录报警时间、地点、处理人） |
| **4. 角色 (Roles)** | 与系统交互的人所扮演的角色（如 `Homeowner`、经理、工程师；若需保存其信息则建类） |
| **5. 组织单元 (Organizational Units)** | 与应用相关的部门、团队、小组（如项目管理软件中的 `Team`、学院/部门组织架构） |
| **6. 地点 (Places)** | 确定问题上下文的物理场所（如制造车间、装卸码头、排课系统中的`教室`——需记录教室编号、座位数） |
| **7. 结构 (Structures)** | 定义一组对象或相关类集合的结构（如`汽车`包含`轮胎`、`发动机`；`ControlPanel` 控制面板）。*老师留思考题：UML 中**组合（Composition）**与**聚合（Aggregation）**有何区别，在 Java/C++ 中分别如何代码实现？* |
