### 1. 软件过程知识的衔接（00:00—06:15）

软件项目需要选择适合项目的过程，并将工作逐层分解：**Process → Activity → Action → Task**。一个活动包含一个或多个动作，一个动作由任务集支持；任务是计划中能够具体执行和跟踪的工作单元。

通用过程框架包括沟通、策划、建模、构建和部署。具体项目通过过程裁剪，确定活动、动作、任务及其顺序。项目规模、需求明确程度、已有经验和技术风险不同，具体过程也会不同。

过程流说明活动如何衔接，任务集说明具体要完成什么工作。**过程模式进一步回答：遇到某类过程问题时，可以采用什么经过实践的方法。**

### 2. 过程模式：把经验转化为可复用资产（06:15—34:30）

#### 2.1 定义与作用

过程模式（Process Pattern）描述软件工程中反复出现的过程问题，说明问题出现的环境，并给出一种或多种解决方案。它可以覆盖整个过程，也可以针对某个活动、动作或任务。

典型问题包括：如何开展需求分析建模、如何组织技术评审、如何进行配置管理、如何设计单元测试用例。团队把成功做法记录为结构化模式，后续成员就能按适用条件查找和使用。

**模式库属于组织的知识资产。**个人经验通过统一模板沉淀下来，可以减少人员流动造成的知识流失，支持复用、培训、质量提升和成本控制。模式需要随实践更新，并按项目情境选用。

#### 2.2 三类过程模式

| 类型 | 关注层次 | 解决的问题 | 例子 |
|---|---|---|---|
| Phase Pattern | 整个过程中的框架活动序列与过程流 | 项目应采用怎样的活动组合、顺序和迭代方式 | 原型开发、螺旋式过程 |
| Stage Pattern | 一个框架活动 | 某个活动如何完成，包含哪些动作与任务模式 | 建立沟通、需求分析建模 |
| Task Pattern | 工程动作或具体任务 | 某项具体工作如何实施 | 需求收集、测试用例设计 |

**区分 Phase 与 Stage 要看覆盖范围。**需求不清时，需要通过多项活动反复迭代来澄清需求，属于 Phase 层次；需求分析建模活动可以包含功能、数据和行为建模等更细的任务模式。

课堂以交易系统的数据采集研究为例：采集运行数据会带来延迟，项目包含研究与开发工作，应围绕低延迟目标安排过程，结合实际约束进行裁剪。

#### 2.3 过程模式模板

| 字段 | 应写清的内容 |
|---|---|
| Pattern Name | 能体现用途的名称，例如 TechnicalReviews |
| Forces | 模式适用的环境、约束，以及影响问题和解决方案的因素 |
| Type | Phase、Stage 或 Task |
| Initial Context | 实施前必须具备的条件、已经完成的工作和已有状态 |
| Problem | 要解决的具体问题 |
| Solution | 解决问题的步骤和实施方法 |
| Resulting Context | 成功实施后达到的状态、形成的结果及后续工作的条件 |
| Related Patterns | 相关模式及其组合、包含或协作关系 |
| Known Uses and Examples | 已知应用场景和实例 |

例如，开展需求分析建模前，客户与工程师应已建立协作关系，需求获取工作应已形成可供分析的输入。需求分析建模还可关联功能建模、数据建模和行为建模模式。

技术评审也是模式可以支持的工作：需求规约等工作产品完成后，通过评审检查质量；评审的组织、检查内容与处理步骤可以进一步形成可复用模板。

### 3. RequirementsUnclear：需求不清的过程模式（34:30—59:50）

#### 3.1 问题与适用条件

客户可能知道要解决什么业务问题，却说不清完整功能、交互方式或处理规则。此时只靠一次面对面交流，很难得到稳定、具体的需求。

**RequirementsUnclear 属于 Phase Pattern。**它通过原型构建与相关方反复评估，使需求逐渐明确，覆盖多项活动及其迭代关系。

实施前需要具备四类条件：

1. 已识别相关方。
2. 已建立相关方与软件团队的沟通方式。
3. 已明确总体上要解决的软件问题。
4. 对项目范围、基本需求和约束已有初步认识。

约束可以涉及外部接口、成本、技术条件和项目边界。“需求不清”仍然需要一个可以开始讨论和验证的问题范围。

#### 3.2 用原型引出需求

> **⚪ 待核实｜00:40:45｜需求不清时采用原型**
> 口头提示（转写摘录）：“注意一下考试本身来考到啊”。

基本路径是：**初步理解需求 → 快速设计与构建原型 → 向客户演示 → 收集反馈 → 调整原型 → 再次评估。**每轮迭代产出一个可展示的结果，帮助相关方确认功能是否解决了实际问题。

原型优先支持需求验证。课堂以学生成绩展示说明：演示阶段可以用文件中的数据支撑界面，正式数据库与完整后台能力在后续工程化时落实。原型的完成标准取决于它要验证的问题。

需求获得认可后，可能有两条路径：

- 原型经过后续增量完善，发展为生产软件。
- 原型完成探索任务后被舍弃，再依据明确的需求采用合适过程开发正式系统。

**能演示功能，不等于已经达到正式交付所需的质量水平。**原型的性能、可靠性和内部结构仍需依据交付要求评估。

#### 3.3 模式的组合与复用

需求不清模式可以关联客户沟通、迭代开发、客户评估、需求提取等模式。快速设计或某个具体开发任务不明确时，可以继续查找更细粒度的模式。

这种层次化组合让团队把“如何开展整个项目”和“如何完成具体任务”连接起来。课堂还提到，需求访谈录音、文本整理与大模型辅助分析可以支持需求获取，但仍需围绕业务问题验证结果。

### 4. 过程评估与改进：CMM 的位置（59:50—76:20）

软件开发采用过程之后，还需要评估过程是否有效，并据此持续改进。评估应关注成本、工期、质量和执行情况；有过程文件，还需要有工程实践与执行证据。

CMM 是 Capability Maturity Model，软件领域常写作 SW-CMM；CMMI 中的 I 表示 Integration。课堂介绍了 CMU 的 SEI 与这些模型的关系，并以 **CMM** 展开五级讲解。

**下面的等级名称和 KPA 采用课堂展示的 CMM 图。**复习时应与 CMMI 的等级命名和过程域体系区分。

| 等级 | 英文名称 | 核心特征 |
|---|---|---|
| 1 | Initial | 初始级：过程控制不稳定，结果较依赖个人经验 |
| 2 | Repeatable | 可重复级：建立基本项目管理，使成功做法可在相似项目中重复 |
| 3 | Defined | 已定义级：形成组织层面的过程定义，并按项目需要实施 |
| 4 | Managed | 已管理级：通过量化指标理解和控制过程与产品质量 |
| 5 | Optimizing | 优化级：依据分析持续改进过程、技术与缺陷预防机制 |

复习主线：**可重复 → 有定义 → 可量化管理 → 持续优化。**更高等级建立在较低等级实践持续有效的基础上。

课件还列出了 SCAMPI、CBA IPI、SPICE 和 ISO 9001 等评估或质量体系相关名称；本讲详细展开的是 CMM 的等级、KPA 与实施案例。

### 5. 从 What to do 到 How to do（76:20—95:20；119:52 起复习）

> **🔴 必考／明确会考｜01:16:47｜CMM 关键过程域及 What to do → How to do**
> 口头提示（转写摘录）：“考试肯定会考”。
>
> **🔴 必考／明确会考｜01:33:04｜KPA 落实：规则、工具、监控与报告**
> 口头提示（转写摘录）：“说会考到二啊”。
>
> **🔴 必考／明确会考｜01:35:14｜CMM 实施、评估与持续改进**
> 口头提示（转写摘录）：“考试会考到啊”。

KPA（Key Process Area，关键过程域）说明需要做好哪些方面，即 **What to do**。组织需要结合自身项目，把要求变成可实施、可跟踪的 **How to do**。

课堂归纳了三个落实方面：

1. **制定规则与制度。**明确对象、职责、时机、步骤和完成要求。
2. **选择并使用工具。**让规则能够在实际工作中执行。
3. **监控执行、形成报告并改进。**依据执行记录和结果评估效果，发现问题后调整做法。

以配置管理为例：应明确哪些需求文档、设计文档和代码进入管理，何时建立版本，修改由谁处理，如何记录变更；再选用工具执行这些规则，并检查执行效果。

工具选择服务于管理目标。安装了工具，还需要有规则、职责、使用记录和效果检查。评估与改进的依据应来自实际执行，而非只看制度是否存在。

### 6. CMM 二级：六个关键过程域（80:45—95:20）

| KPA | 核心要求与课堂案例 |
|---|---|
| Requirements Management | 需求管理：记录、跟踪需求及其新增、删除、修改，保持开发依据清楚 |
| Software Project Planning | 软件项目策划：定义活动、动作、任务，形成可以执行的项目计划 |
| Software Project Tracking and Oversight | 软件项目跟踪与监督：检查实际执行与计划的差异，跟踪进度和问题 |
| Software Subcontract Management | 软件子合同管理：对外包工作的约定、执行和交付进行管理 |
| Software Quality Assurance | 软件质量保证：在工作产品形成过程中检查过程是否遵守规范 |
| Software Configuration Management | 软件配置管理：管理工作产品、版本和变更，使其状态可追踪 |

**质量保证贯穿形成过程。**例如，在数据库设计、需求分析或编码尚未完成时，检查工作是否按规定执行，代码是否有设计依据。完成后的同行评审则进一步检查工作产品本身。

可重复级强调把有效的项目管理做法保留下来，在后续相似项目中继续使用。每个 KPA 都需要通过规则、工具、监控与报告落实。

### 7. CMM 三级：七个关键过程域（121:15—139:50）

| KPA | 理解要点 |
|---|---|
| Organization Process Focus | 组织过程焦点：组织持续关注过程，推动评估与改进 |
| Organization Process Definition | 组织过程定义：明确过程、活动、动作与任务，并形成可使用的过程资产 |
| Training Program | 培训计划：让人员具备项目需要的业务和技术能力，并检查培训效果 |
| Integrated Software Management | 集成软件管理：协调项目的管理工作与工程工作，统一考虑计划、投入和成本 |
| Software Product Engineering | 软件产品工程：协调需求、设计、实现和测试等工程活动，形成一致的产品工作成果 |
| Intergroup Coordination | 组间协调：明确不同角色或小组的沟通、交接和协作机制 |
| Peer Reviews | 同行评审：由具备相关能力的人员检查工作产品，及早发现问题 |

#### 7.1 过程定义与培训

过程定义要落实到项目实际：需求不清时，可以把原型迭代纳入需求获取；缺少类似项目经验时，需要更细致地定义测试设计、执行和跟踪工作。

培训覆盖新业务、新架构、数据库、编程语言和工具等内容。培训同样需要计划、执行支持和效果检查。

#### 7.2 集成软件管理与产品工程

> **🟠 经常考／曾考过｜02:07:38｜集成软件管理：管理投入计入项目成本**
> 口头提示（转写摘录）：“你说这考试考考好几次了”。

课堂通过项目经理、SQA 人员和检查人员的投入说明：管理工作可能分散在整个开发周期中，相关工时和成本也应纳入项目考虑。不能只统计连续编码工作的投入。

在软件产品工程的讨论中，课堂还比较了客户定制项目与面向多个用户的产品，并引出公共模块复用、可变部分管理和产品化的问题。

#### 7.3 协调与同行评审

代码修改往往涉及开发、复查、测试和重新提交。协作机制要明确谁接收任务、何时完成、如何反馈；工具可以支持自动通知和任务流转。

**同行评审是静态检查。**需求规约、设计文档和代码等工作产品均可接受评审。代码评审可以检查逻辑、变量定义与使用等问题；需求和设计阶段的评审可以减少错误向后续阶段传递。

课堂特别强调：只在最后检查代码，可能发现问题源自更早的需求或设计，因此工作产品应在形成后及时评审。

### 8. 拓展：智能研发与智能运维（139:50—148:10）

课堂展示了“面向软件全生命周期的智能研发与运维”研究，包含两条方向。

**智能研发：**围绕需求获取、需求分析、概要设计、详细设计、编码和各层次测试安排智能体，并通过主控协调形成流程。其与软件过程的联系在于：明确各阶段输入、输出、任务关系与检查要求。

**智能运维（AIOps）：**面向运行中的系统，利用日志、指标和其他观测数据识别异常，定位根因，支持故障处理与报告。展示内容包括多模态数据分析、异常检测、流量问题、故障分析、知识图谱和故障报告生成。

展示的协作结构包含观测、检测、诊断等智能体。课堂以交易系统为例强调，异常发现、根因定位和处置速度直接关系到业务运行；采集观测数据本身也需要控制开销。

### 9. CMM 四级：定量管理（148:10—155:40）

四级包含两个 KPA：**Software Quality Management（软件质量管理）**与 **Quantitative Process Management（定量过程管理）**。

定量管理把“效果怎样”转化为可测量、可比较的问题。可关注缺陷数量与严重性、工时、成本、进度偏差和管理投入比例，并与组织基准比较。

#### 9.1 缺陷密度示例

若 1000 行代码发现 10 个缺陷，则每百行代码的缺陷数为：

$$D_{100}=\frac{10}{1000}\times100=1$$

这是**每百行代码 1 个缺陷**的密度指标。课堂用组织内部基准说明如何识别偏差；具体阈值应来自项目要求和组织数据。

#### 9.2 偏差需要解释

计划三天完成而实际两天完成，也需要分析：工作效率提升、估算偏大、范围变化或检查不足，都可能影响解释。只看提前或延期，无法判断过程质量。

管理成本占比也可以作为分析对象。课堂以计划比例和实际比例不同为例，说明应结合项目难度与管理方式寻找原因，而非只报告一个数字。

量化结果用于发现问题、分析原因和选择改进措施。质量之外，工作量、成本和其他过程表现也应纳入适当的量化管理。

### 10. CMM 五级：优化与缺陷预防（155:40—163:15）

| KPA | 改进方向 |
|---|---|
| Process Change Management | 过程变更管理：根据执行反馈改进活动、动作和任务安排 |
| Technology Change Management | 技术变更管理：评估并有序引入技术变化，管理其影响 |
| Defect Prevention | 缺陷预防：分析缺陷根因，采取措施减少同类问题再次出现 |

过程优化可以表现为调整测试步骤或增加必要检查。技术变化可能牵涉数据库、接口和应用代码，需要识别影响并控制迁移；成熟的过程为实施变化提供支持。

#### 10.1 用鱼骨图追查根因

面对一个缺陷或运行异常，可以先列出若干可能原因，再继续追查每个原因的下层原因，直到定位可采取措施的根因（Root Cause）。

课堂以数据库设计问题为例：若进一步分析发现问题与范式知识或设计方法有关，就应改进设计规则、评审或培训。**修复当前缺陷与预防再次发生，需要分别落实。**

缺陷预防的路径是：**识别问题 → 分析根因 → 制定针对性措施 → 执行并检查效果 → 沉淀到组织实践。**

### 11. 自测题

1. Phase、Stage、Task 三类模式按什么区分？——分别关注活动序列与过程流、框架活动、工程动作或任务。
2. RequirementsUnclear 为什么属于 Phase Pattern？——它需要多项活动和多轮迭代共同澄清需求。
3. Initial Context 与 Resulting Context 有何区别？——前者是实施前条件，后者是成功实施后的状态。
4. 原型认可后有哪些去向？——逐步完善为正式软件，或舍弃原型后重新开发。
5. KPA 与具体实施方法是什么关系？——KPA 指明要做好什么，组织把它落实成适合自身的做法。
6. 课堂归纳的 How to do 三方面是什么？——规则制度、工具支持、监控报告与改进。
7. CMM 二级有几个 KPA？——六个：需求、计划、跟踪监督、子合同、质量保证、配置管理。
8. 为什么项目经理与 SQA 的零散投入也要记录？——它们属于实际项目工作，会影响工时、成本和管理判断。
9. 同行评审为什么应覆盖需求与设计？——上游缺陷会传递到实现阶段，早期发现有助于减少后续返工。
10. 四级的关键特征是什么？——用量化数据管理产品质量与过程表现。
11. 五级如何预防同类缺陷？——追查根因，改进规则、方法或培训，并检查措施效果。
12. 本讲列出的二级 Repeatable、三级 Defined 应按哪个体系复习？——课堂展示的 CMM 体系。
