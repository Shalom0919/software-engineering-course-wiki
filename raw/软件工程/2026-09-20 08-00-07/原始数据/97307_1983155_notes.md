### 1. 软件的组成与应用领域（00:00—12:00）

#### 1.1 软件的三部分

软件包含**程序、数据和文档等相关工作产品**。程序实现处理逻辑，数据按适当结构组织，文档记录需求、分析、设计、测试等开发依据。

需求获取形成需求规约；需求分析建模形成分析规约；架构设计和详细设计也有相应工作产品。系统交付后的运行、维护和改进，需要这些资料帮助理解功能、结构与实现依据。

#### 1.2 七类应用领域

| 领域 | 核心作用 | 课堂或课件例子 |
|---|---|---|
| System Software | 支撑计算环境、管理资源与运行 | 操作系统、驱动、网络路由相关软件 |
| Application Software | 解决特定业务问题 | 医院服务、具有具体业务功能的应用 |
| Engineering / Scientific Software | 支持工程分析、科学计算和复杂数据处理 | 气象预测、分子生物、工程分析 |
| Embedded Software | 嵌入产品或系统，控制功能与行为 | 汽车、微波炉中的控制软件 |
| Product-line Software | 面向一类市场或任务，以共享能力支持多个相关产品 | 具有共性能力的软件产品系列 |
| Web / Mobile Applications | 通过网络或移动设备提供应用能力 | 浏览器应用、移动端应用 |
| Artificial Intelligence Software | 用智能方法处理推理、识别等问题 | 专家系统、模式识别、神经网络、大模型应用 |

这些类别提供理解软件应用领域的视角。具体业务还可以按交通、政务、办公等领域分类；分类口径应与讨论目的对应。

### 2. 遗留软件及其演化（12:00—34:20）

#### 2.1 遗留软件的特点

遗留软件（Legacy Software）通常开发较早，经过长期使用和持续修改，仍承担业务功能。其架构、数据库或实现技术可能已较陈旧，维护成本与演化风险逐渐突出。

两个重要特点是：

- **寿命长（Longevity）：**系统经过多年使用，积累了功能、数据和变更。
- **业务关键性（Business Criticality）：**系统支撑核心业务，组织难以直接停用。

课堂以较早的 C/S 系统说明历史技术与新需求之间的关系。判断遗留软件，需要结合使用历史、技术状态、业务依赖与维护问题，不能单凭架构名称判断。

#### 2.2 质量问题覆盖整个软件

遗留系统可能存在难以扩展的设计、复杂代码、文档缺失、测试用例与结果保存不全、变更记录混乱，以及数据管理问题。

软件质量需要同时检查程序、数据和工作产品。例如，只有代码而缺少需求与设计依据，会增加定位问题和评估变更影响的难度；测试资料缺失，则会削弱后续回归验证的依据。

**系统运行可靠、满足用户需求时，可以继续使用；演化由实际业务与技术变化驱动。**是否改造，需要结合收益、成本、风险和业务连续性判断。

#### 2.3 修改与演化的关系

常见修改包括：

| 修改方向 | 含义 | 例子 |
|---|---|---|
| Correct | 纠正缺陷 | 修复错误处理或错误计算 |
| Adapt | 适应环境变化 | 适应平台、政策或业务规则变化 |
| Enhance | 增强能力 | 增加功能、满足新增需求 |

系统在反复修改中形成新的版本与能力，这构成持续演化。每次修改都需要评估对原有行为、数据与接口的影响。

#### 2.4 四类主要演化原因

> **⚪ 待核实｜00:28:28｜遗留软件演化原因**
> 口头提示（转写摘录）：“第二个，这考试我才考到啊”。

1. **适应新的计算环境或技术。**环境变化要求系统进行相应调整。
2. **实现新的业务需求。**增加或完善功能，支持业务发展。
3. **与更现代的系统或数据库互操作。**扩展接口和协作能力。
4. **重新组织体系结构。**使系统能够在变化的计算环境中继续发挥作用。

课堂以 C/S 向 B/S 等架构调整说明第四类变化。接口扩展和整体架构调整涉及的范围不同，承接改造任务时应先确认具体变化、依赖关系和交付目标。

### 3. 软件形态的变化：Web 与移动应用（34:20—41:00）

#### 3.1 Web 应用

早期 Web 主要提供相互链接的文本与图像。随着开发技术发展，Web 系统逐渐具备计算、交互和业务处理能力。

课件通过语义 Web 等内容引出 Web 技术的演进，并布置小组查阅 Web 发展史。复习时应关注各阶段能力如何变化，以及这些变化对应用开发提出了什么要求。

#### 3.2 移动应用

移动应用通常结合用户界面、网络资源访问、本地处理与存储。前端和后端的分工取决于业务与设备能力，例如从服务器取得数据，在手机上完成交互、处理与展示。

| 形式 | 主要使用方式 | 关注点 |
|---|---|---|
| Mobile Web Application | 通过移动浏览器访问 | 页面适配、网络访问和交互 |
| Mobile App | 安装在移动平台运行 | 平台接口、设备能力、本地处理与持久化 |

移动应用可以使用位置、加速度等设备能力。设计时需要明确哪些工作在本地完成，哪些工作依赖后端服务。

### 4. 云计算与云平台架构（41:00—60:40）

#### 4.1 云平台要解决的问题

云平台通过资源共享和虚拟化支持按需使用，并根据负载变化调整资源。其工程目标包括服务质量、资源利用率和运行成本之间的协调。

例如，并发请求上升时需要增加处理能力；负载降低时可以释放资源。监测、预测、调度与反馈构成持续管理过程。

#### 4.2 三类服务与实现层次

| 服务 | 英文全称 | 理解重点 |
|---|---|---|
| IaaS | Infrastructure as a Service | 提供计算、存储、网络等基础资源能力 |
| PaaS | Platform as a Service | 提供应用开发与运行所需的平台能力 |
| SaaS | Software as a Service | 向用户提供可直接使用的应用服务 |

课堂还从实现角度划分资源层、虚拟层、中间件层和应用层。**服务模型说明对外提供什么能力，实现分层说明系统内部如何组织。**两种划分可以结合理解。

资源层包含服务器、计算、存储和网络设施；虚拟化使物理资源能够按需组织；平台层承担运行支持、资源管理等工作；应用层承载用户业务。

#### 4.3 监测、预警与调度

课堂围绕平台管理归纳了三项工作：

1. **资源监测：**观察 CPU、内存、请求量等运行情况，收集日志和指标。
2. **预警与预测：**识别异常或容量压力，为调整资源提供依据。
3. **优化决策：**根据目标和约束执行扩缩容、调度或迁移。

CPU 使用率阈值是课堂用于解释预警的示例，具体阈值需要结合业务负载和服务目标确定。

Kubernetes（K8s）作为容器编排与管理工具出现在课堂讨论中，用于说明自动化部署、扩缩容和运行管理。监测、预测与优化能力通常需要结合相应工具和算法实现。

### 5. 拓展案例：云平台变更风险与智能运维（60:40—75:50）

#### 5.1 问题背景：受限观测

云平台能够掌握部分基础设施运行信息，但租户的业务语义、应用内部指标或调用关系可能无法完整获得。底层硬件、平台软件或配置更新，却可能影响上层应用。

因此，变更前需要回答两个不同问题：**哪些对象重要？这次变更可能带来多大风险？**重要性帮助分配关注程度，风险评估帮助制定具体变更策略。

#### 5.2 云主机节点画像

课堂展示“基于多维特征的云主机节点画像算法”。主机、虚拟机和应用之间的映射与依赖较复杂，需要结合可观测特征分析对象之间的关系和重要性。

如果某个主机承载关键应用或关键依赖，更新该主机时就需要重点关注。画像结果可用于确定监测重点和变更安排。

#### 5.3 业务应用动态健康评估

另一项研究关注变更的影响传播和业务风险。挑战包括异构关系建模、复杂传播路径，以及应用侧数据获取受限。

课堂展示了结合图关系、时序信息和风险评分的研究方案。输出可用于变更前评估、变更中动态监测，以及必要时调整或暂停变更。

这个案例体现了**智能运维（AIOps）**的工程目标：利用数据和模型辅助运行维护决策，同时把模型结果接入实际运维过程。

### 6. 软件产品线与系统化复用（75:50—84:10）

软件产品线（Software Product Line）面向具有共同特征的一组软件产品，通过受管理的共享资产支持开发。

**复用资产覆盖整个生命周期。**课堂以政务等同类业务系统为例，列出可沉淀的内容：

- 需求规约和共性功能描述。
- 架构与数据设计、设计模式。
- 标准类、构件、代码模块。
- 测试用例、测试方法和相关工程工作产品。

组织需要将资产标准化，存入便于查找的库或仓库，说明用途、接口与使用方式。新项目通过选择、配置、适配和集成这些资产构建产品，并处理自身特有需求。

软件产品线强调共性与可变性的管理。其价值来自可持续使用的工程资产，以及围绕这些资产建立的开发过程。

### 7. 软件工程的定义（84:10—95:20；119:55—135:10）

> **🔴 必考／明确会考｜01:30:55｜软件工程定义：系统化、规范化、可量化**
> 口头提示（转写摘录）：“这个这样会考到”。

软件工程包括两个层面：

1. 将**系统化、规范化、可量化**的方法应用于软件的开发、运行和维护。
2. 研究上述方法。

三个关键词分别是 **Systematic、Disciplined、Quantifiable**。定义的适用范围贯穿开发与后续运行维护，课堂的云平台变更案例就属于维护场景。

#### 7.1 Systematic：系统化

系统化要求工作具有合理结构、依赖关系和衔接方式。需求获取、分析、设计、实现、各层次测试与交付之间需要有明确输入和输出。

数据库设计案例说明了这种组织方式：理解需求、识别实体与关系、形成概念模型、完成逻辑设计及必要的规范化，再进入物理设计。

系统化并不要求所有项目使用同一种固定流程。过程要结合项目规模、业务和风险进行适应性调整。

#### 7.2 Disciplined：规范化

规范化要求方法按明确规则执行。课堂以单元测试为例：

1. 阅读被测单元的详细设计，理解功能与约束。
2. 选择适合的测试设计方法，如边界值分析、等价类划分。
3. 按方法规则设计测试用例，写清输入与预期结果。
4. 评审测试用例集，纠正设计问题。
5. 执行测试，比较结果，记录并跟踪问题。

测试用例集本身也需要质量检查。错误的预期结果会影响对被测程序的判断。

#### 7.3 Quantifiable：可量化

可量化要求用数据描述工作与结果，并据此进行比较、跟踪和改进。

**例一：三角形测试。**输入三条边为 5、5、13 时，因为 $5+5<13$，预期结果应为“非三角形”。测试记录需要区分输入、预期结果和实际结果。

| 测试项 | 示例 |
|---|---|
| 编号 | 001 |
| 输入 | 5、5、13 |
| 预期结果 | 非三角形 |
| 实际结果 | 执行程序后记录 |
| 判定依据 | 实际结果是否符合预期 |

如果测试用例把预期结果写成某类三角形，应先纠正用例。课堂进一步假设 20 个用例中发现 3 个设计错误，用明确数量支持评审与纠正跟踪。

**例二：工作量偏差。**需求获取及其评审计划投入 3 人天，实际投入 4 人天，则实际比计划多 1 人天。计划、实际、差异和原因应一起记录，作为后续估算与改进的依据。

#### 7.4 方法研究与适应性

测试、建模、数据库设计，以及利用大模型辅助工程活动的方法，都可以成为软件工程研究对象。方法使用需要兼顾规范与适应性，结合团队和项目条件落地。

### 8. 软件工程的四层结构（135:10—146:50）

从下向上，软件工程的分层技术结构是：**质量关注 → 过程 → 方法 → 工具**。

| 层次 | 作用 | 例子 |
|---|---|---|
| Quality Focus | 提供持续关注质量的基础 | 检查工作成果是否满足质量要求 |
| Process | 组织工作与衔接，支持管理和控制 | 需求、设计、构建、测试等活动安排 |
| Methods | 提供完成工程任务的技术方法 | 需求获取、建模、设计、测试方法 |
| Tools | 为过程和方法提供自动化或半自动化支持 | 建模工具、测试工具、集成工具链 |

过程确定工作如何组织，方法说明具体怎样完成，工具帮助执行和协作。各层共同服务于质量目标。

**CASE（Computer-Aided Software Engineering）**指计算机辅助软件工程。工具集成后，一个工具形成的信息可以供其他工具使用，支持软件开发中的信息衔接。

课堂还讨论了将需求获取、需求分析等工作组织为智能体，并集成多种工具。需求区分、规约形成、评审与确认仍需在工程流程中明确安排。

### 9. 回归测试与用例集维护案例（146:50—153:40）

产品持续发布新版本后，需要检查修改及其影响。课堂以一个拥有约 4000—5000 个系统测试用例的企业项目说明，每次发布执行全部用例会产生较大工作量。

该案例关注回归测试中的用例选择与维护：

1. **分析版本变更。**明确功能、代码、接口等发生了什么变化。
2. **查找相关用例。**建立变更与已有测试用例的联系。
3. **分类处理。**部分用例可以直接执行，部分需要修改。
4. **补充新用例。**为新增功能或接口补足验证。
5. **形成并执行本次回归用例集。**验证变化及受影响行为。

**用例选择取决于变更影响分析。**课堂中从 5000 个用例筛出约 1000 个的数字用于说明任务规模，重点是识别直接执行、修改后执行和新增三类工作。

大模型可以辅助关联分析和用例处理；工具效果需要通过实际测试过程验证。自动化的价值在于减少重复劳动，并支持更有效的验证。

### 10. 软件过程：Activity、Action 与 Task（153:40—164:49）

过程（Process）由活动、动作和任务构成，用于产生工作产品。工作分解逐步降低粒度，使职责、执行内容和检查对象更明确。

| 层次 | 含义 | 课堂例子 |
|---|---|---|
| Activity | 面向较宽目标的工程活动 | 需求分析建模 |
| Action | 活动中具有明确目标的一组工作 | 功能建模 |
| Task | 可具体执行的工作任务 | 了解建模工具、构建模型、评审模型 |

一个 Activity 可以包含一个或多个 Action；一个 Action 可以包含一个或多个 Task。

#### 10.1 需求分析建模的五个动作

课堂将需求分析建模活动分解为：

1. 功能建模。
2. 状态或行为建模。
3. 数据建模。
4. 形成需求分析规约。
5. 评审规约。

其工作产品是需求分析规约，模型与文字说明共同支持后续设计。

#### 10.2 功能建模的三个任务

功能建模动作进一步分解为：

1. 了解并准备建模工具。
2. 完成功能模型。
3. 对照需求评审模型，检查是否准确表达所需功能。

这一例子同时体现系统化与规范化：工作有分解、有顺序、有产出，并通过评审检查结果。

### 11. 自测题

1. 软件的三部分是什么？——程序、数据和文档等相关工作产品。
2. 遗留软件为何难以直接停用？——它往往承载核心业务，并积累了数据和依赖。
