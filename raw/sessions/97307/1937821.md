- 区分管理者、客户和开发者的软件误区，并能解释其实际后果。
- 掌握线性、迭代、演化、并行四种过程流。
- 根据项目情况裁剪过程，再定义 Activity、Action 和 Task；理解任务集、工作产品、质量保证点与里程碑。

### 1. 工程实践四步的复习（00:00—22:00）

| 实践 | 工程活动 | 关键检查 |
|---|---|---|
| 理解问题 | 需求获取与需求分析建模 | 是否理解客户目标、功能、数据及非功能要求 |
| 制定方案 | 概要设计、详细设计 | 是否形成能够指导实现的方案 |
| 执行方案 | 编码 | 代码是否以详细设计为依据，是否经过评审 |
| 检查结果 | 测试与结果核对 | 是否选择适当方法，验证功能和质量要求 |

#### 1.1 概要设计的三个方面

课堂以图书馆系统说明概要设计涉及**体系结构、数据设计、接口设计**。结构图展示前端、后端、数据库和子系统；接口涉及系统内部协作，以及与校园卡、教务、OA 等外部系统的交互。

详细设计说明构件、类和方法内部的实现依据。代码应能追踪到相应设计；评审应检查逻辑、接口及关键算法是否正确。

#### 1.2 边界值与等价类

**年龄输入框：边界值测试。** 在合法范围的边界、边界附近、范围内部，以及越界位置选择数据，检查接受和拒绝行为。具体上下界由需求规定，课堂中的年龄数值用于演示选值思路。

**学生分类：等价类划分。** 若某项业务对不同学生类别具有不同规则，可以按相关规则划分等价类，在各类中选代表进行测试。等价性取决于被测功能，不能只依据名称随意分组。

#### 1.3 系统级测试

图书馆系统需要验证借书、还书、打印借阅清单、毕业清退等业务。同时检查性能等非功能要求，例如模拟大量学生同时访问。

测试还要考虑基础数据是否正确装载，并把结果与利益相关方要求对照。测试用例的价值在于覆盖实际规则与风险，而不只是增加用例数量。

### 2. 面向整个项目的实践原则（22:00—31:00）

课堂讨论七项宏观原则，强调它们适用于项目整体。

| 原则主题 | 课堂展开 |
|---|---|
| 软件存在的价值 | 判断系统是否对客户有用，考虑开发的必要性与可行性 |
| 保持简单：KISS | 让活动、模型与工作产品清楚易懂，减少无必要的复杂性 |
| 保持愿景：Maintain the Vision | 课堂借助可见的模型和文档讨论系统整体认识；共同理解系统结构与方向 |
| 成果会被他人使用 | 考虑数据交换、系统接口，以及成果的后续使用者 |
| 面向未来开放 | 为适应、增强和外部系统连接保留合理的扩展空间 |
| 提前考虑复用 | 整理、重构和标准化通用构件，形成可复用资产 |
| 思考 | 通过思考、讨论和交流改进决策 |

接口开放的例子：图书馆系统若需要连接其他图书资源，早期设计应考虑相应接口，否则后续改造成本可能增加。

### 3. 软件误区：Myths 与现实（31:00—66:00）

#### 3.1 管理者误区

| 误区 | 现实与后果 |
|---|---|
| 标准、规程齐全，就能开发好软件 | 还要让团队理解并使用标准，通过管理和跟踪检查执行 |
| 项目落后，增加人员就能追回进度 | 新成员需要学习，原成员需要指导，沟通开销增加，可能进一步延误 |
| 项目外包后即可放手 | 外包部分仍需统一管理进度、质量和接口，否则集成时可能发现未完成或无法使用 |

增加人员的效果取决于任务划分、经验和协作条件，不能把人数直接换算成进度提升。

#### 3.2 客户误区

**简单目标描述就足够开始全面实现。** 实际需求常有模糊、遗漏和冲突，需要通过需求获取与分析逐步澄清。客户应参与需求确认。

**软件容易修改，所以需求可以随时无成本变更。** 变更会影响设计、代码、测试及进度。敏捷可以组织和吸收变化，但新的要求通常需要评估优先级并安排到合适的迭代。越晚引入的变更，通常涉及更多已经完成的工作。

#### 3.3 开发者误区

| 误区 | 课堂强调 |
|---|---|
| 代码能运行，工作就结束 | 交付、维护、数据和文档等工作仍需完成 |
| 运行之前无法评价软件质量 | 需求、分析、设计等成果可以通过质量保证与评审检查 |
| 唯一交付物是可运行程序 | 软件还包含数据及描述性信息，需要交付相关工作产品 |
| 工程文档只会拖慢开发 | 必要文档保存依据、支持维护并减少返工，详细程度应适合项目 |

质量沿开发过程传递：需求问题可能影响分析，分析问题影响设计，设计问题影响代码。各阶段的 SQA 和评审形成质量检查点；代码还可以通过动态测试检查。

### 4. 四种过程流（66:00—79:00）

过程定义有哪些活动；过程流（Process Flow）描述这些活动如何随时间组织。

| 类型 | 特征 | 课堂例子 |
|---|---|---|
| 线性 Linear | 按顺序向后推进 | 需求十分明确时，沿需求、设计、实现、交付依次开展 |
| 迭代 Iterative | 某些活动重复执行或返回前面活动 | 编码时发现详细设计问题，返回修改后继续实现 |
| 演化 Evolutionary | 经历多轮开发与发布，逐步完善产品 | 先交付基础能力，再根据反馈增加功能和改善质量 |
| 并行 Parallel | 相容活动或不同部分的工作同时进行 | 编码与相关单元测试准备交叉开展 |

迭代强调重复、反馈与修正；演化强调产品在一轮轮交付中增长和改进。并行需要协调依赖。课堂用螺旋上升来解释演化，但这里讨论的是过程流，不直接等同于某个具体过程模型。

### 5. 框架活动如何定义（79:00—约127:00）

先根据项目规模、复杂度、人员及利益相关方情况裁剪标准过程，确定需要的活动；再定义每项活动包含哪些动作，每个动作包含哪些任务。

**Process → Activity → Action → Task** 是组织工作的层次。明确任务后，可以分配负责人、安排开始和结束日期，并形成整体计划。

#### 5.1 本讲对教材对应关系的修正

| 教材术语 | 本讲明确的对应关系 |
|---|---|
| Communication | 需求获取／需求诱导 |
| Modeling | 需求分析建模、概要设计建模、构件级设计建模 |
| Construction | 编码与测试 |
| Deployment | 发布、交付及支持 |

**需求工程 = 需求获取 + 需求分析等相关工作。** 本讲把需求分析建模明确放入 Modeling；这修正了前次课堂将它与 Communication 放在一起解释的方式。Planning 仍在课堂管理维度中重点讨论。

#### 5.2 极小项目：一次电话沟通包含四项任务

对于单人开发、需求简单明确的项目，Communication 可以采用一个 Phone Conversation 动作：

1. 联系相关利益相关方。
2. 讨论需求并记录。
3. 整理为简短的书面需求说明。
4. 将说明发给相关方评审、修改并批准。

完成这些任务后形成需求成果，为后续工作提供依据。简单项目也需要明确的工作组织和需求确认。

#### 5.3 更复杂项目

复杂项目需要更丰富的动作。课堂提到启动、需求获取、细化、协商、规格说明、确认等内容。动作内部继续细分任务，并结合项目情况安排执行。

同一个活动名称并不意味着所有项目都执行同样数量的任务；需要选择适合当前项目的工作粒度。

### 6. 任务集与里程碑（约127:00—134:00）

> **🔴 必考／明确会考｜02:11:41｜任务集、工作产品与里程碑**
> 口头提示（转写摘录）：“考试会考”。

任务集（Task Set）不仅描述要做的任务，还联系工作产品、质量保证点和项目里程碑。选择任务集时，应考虑当前动作的目标及项目特点。

**里程碑（Milestone）**标记某个重要状态达到。课堂用项目管理工具中的零工期、菱形标记示例，表示相关活动完成，所需工作产品已经形成并可供下一阶段使用。

里程碑本身是检查和标记点，前面的实质工作由具体任务完成。设置里程碑时需要定义完成条件，才能据此判断阶段状态。

### 7. 需求获取任务集：小项目与大项目（134:00—163:00）

#### 7.1 简单项目的六项任务

> **🟡 出题示例｜02:17:27｜需求获取的参与者与任务**
> 口头提示（转写摘录）：“如果如果如果考试给一个多数选择题”。

1. 列出项目的利益相关方。
2. 通过非正式讨论收集需求。
3. 列出功能和非功能要求。
4. 讨论并完善需求清单。
5. 排定需求优先级。
6. 记录尚未明确的问题和不确定区域。

这组六项任务描述 Requirements Gathering 动作；它与前面“电话沟通四任务”的例子具有不同的工作划分，不能混为一张固定模板。

优先级支持增量交付：先完成当前最重要的需求，其他需求放入后续迭代。不确定项需要明确记录并继续澄清。

#### 7.2 图书馆案例中的需求

- 利益相关方包括实际用户、图书管理人员、系统管理人员，以及与项目有关的供应商等。
- 功能包括图书管理、借阅、出版社管理、报表等。
- 非功能要求包括性能、安全和兼容性；可测量的要求应给出具体条件与指标。
- 约束包括借阅数量、毕业前还清图书等业务规则，以及预算、技术选型等限制。

#### 7.3 复杂项目的细化任务

课堂以十二项任务示例说明复杂项目需要更细致的组织：识别相关方、分别访谈、形成初步需求清单、安排协调会议、开展会议、建立使用场景、根据反馈细化场景、更新需求清单、进一步完善需求、组织需求包、记录约束、约定确认方法。

其中个别任务的英文表述识别不清，以上保留可确认的工作内容。

**使用场景与用例图**帮助表达参与者及其需要的功能。图书管理员和学生的权限与使用目标不同，应通过相关方反馈修正。用例图表达参与者与用例关系，具体场景还需要说明交互过程。

需求可以按业务能力组织为包，便于分阶段交付。需求确认需要检查内容和约束是否准确，并取得相关方认可。

### 8. 过程模式的引入（末尾）

过程模式（Process Pattern）把已经有效解决某类过程问题的方法整理为可参考的结构与步骤。团队遇到类似问题时，可以查找适用模式并结合上下文采用。

本讲末尾只作引入，具体模式结构留到后续课堂。

### 9. 自测题

1. 年龄输入框为何适合边界值测试？——边界及越界位置容易暴露范围判断问题。
2. 等价类为何要结合被测功能划分？——同类数据在该功能下应具有相近的处理行为。
3. 项目延期后增加人员为何可能更慢？——学习、指导和沟通增加额外工作。
4. 外包后还需管理什么？——进度、质量、接口、交付和集成要求。
5. 迭代流与演化流的重点区别是什么？——前者强调重复修正，后者强调多轮发布中的产品发展。
6. 本讲如何修正 Communication 与 Modeling 的对应？——获取属于前者，分析建模与设计属于后者。
7. 电话沟通四任务与需求获取六任务为何不同？——它们对应不同项目情境和动作划分。
8. 里程碑为何通常设为零工期？——它标记达到状态，实际工作由前面的任务承担。
9. 为何需要记录不确定需求？——使未决问题可追踪，供后续迭代澄清。
10. 交付包为何要有明确约束？——确保业务规则、成本、技术等条件被纳入开发和确认。
