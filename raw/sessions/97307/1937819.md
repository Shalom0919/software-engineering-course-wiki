### 1. 为什么会编程还不够（00:00—08:11）

编程语言解决程序的表达和实现问题。大型软件还需要确定需求范围、划分子系统、设计数据和接口、协调开发工作、验证质量并持续维护。银行、税务、电商等系统具有复杂业务、多系统交互和大量数据，仅掌握一种语言不足以完成可靠交付。

工程思想把复杂任务组织成相互衔接的活动：每项活动具有目标、输入和输出，前一活动的成果为后续活动提供依据。开发中产生的需求、设计和测试文档也是交付成果。

大语言模型可以辅助编码、需求信息整理等工作，但工程问题仍包括“究竟要做什么”“怎样组织系统”和“如何验证结果”。生成代码只是其中一个环节。

### 2. 软件开发全过程（08:11—56:00）

| 阶段 | 英文术语 | 主要任务 |
|---|---|---|
| 1. 需求获取 | Requirements Elicitation / Gathering | 调研用户目标、业务规则、功能与非功能需求，明确范围 |
| 2. 需求分析与建模 | Requirements Analysis and Modeling | 从数据、功能、行为等角度抽象需求，建立对系统的理解 |
| 3. 概要／架构设计 | High-Level / Architectural Design | 确定整体结构、子系统划分及其协作关系 |
| 4. 详细／构件级设计 | Detailed / Component-Level Design | 明确类、方法、接口、内部逻辑，必要时使用伪代码 |
| 5. 编码 | Coding | 将设计实现为可执行程序 |
| 6. 单元测试 | Unit Testing | 检查单个单元的功能与内部逻辑 |
| 7. 集成测试 | Integration Testing | 检查多个单元组合后的接口与协作 |
| 8. 系统测试 | System Testing | 在目标环境中验证整体功能及性能、安全性等要求 |
| 9. 验收测试 | Acceptance Testing | 从用户和业务需求角度检查系统是否可接受 |
| 10. 发布／交付 | Release / Delivery | 将系统交付或部署供使用 |
| 11. 支持／维护 | Support / Maintenance | 持续纠错、适应环境变化并增强功能 |

这是一条理解工程活动的主线。实际项目可以根据特点裁剪过程，阶段之间也可能反复迭代；发现需求或设计问题时，需要回到前面的活动调整。不能把这张表理解成所有项目都必须一次性顺序完成的固定流程。

#### 2.1 需求获取：回答“要做什么”

客户的一句“做一个新的财务系统”不足以直接指导实现。需要追问业务目标、涉及的用户、具体功能、质量要求和系统边界。需求信息可能来自访谈、文字、音频、视频及现场讨论，需要整合。

功能需求描述系统提供什么服务；非功能需求描述系统应具备怎样的质量和约束，例如性能、安全性。调研阶段遗漏这些要求，会影响后续设计和验收。

#### 2.2 需求建模：从不同角度理解同一系统

| 视角 | 关注问题 | 课堂例子 |
|---|---|---|
| 数据模型 | 系统处理哪些数据，数据之间有何关系 | 实体与联系；从 ER 模型理解数据组织 |
| 功能模型 | 系统完成哪些处理，处理逻辑是什么 | 流程图中的顺序、分支和循环 |
| 行为／状态模型 | 对象有哪些状态，什么事件引起转换 | 学生注册、在学、休学、毕业等状态 |

建模是一种抽象：教育经历和身体健康可以分别建模，同一个对象也可以从不同角度描述。模型的选择服务于理解问题，而不是把全部现实细节画进去。

**需求分析侧重理解系统应该做什么；设计侧重决定如何实现。** 数据库表和模块结构应有需求与模型依据，避免只凭直觉随意确定。

#### 2.3 概要设计与详细设计的区别

概要设计关注大的结构与职责划分。仅说“采用前后端架构”往往不足以描述复杂系统，还需要说明后端如何划分子系统、各部分如何合作，以及结构如何支持性能等要求。

详细设计进一步落实到构件、类和方法，说明输入输出、接口、调用关系和内部处理逻辑。一次业务操作可能跨越多个类、多个方法甚至多个子系统。

#### 2.4 四类测试如何区分

单元测试检查局部实现；集成测试检查组合与接口；系统测试检查整个系统在目标环境中的行为；验收测试检查交付结果是否满足用户需要。

接口既包括内部方法之间的调用，也包括数据库访问以及与支付、地图等外部服务的交互。单个模块能够正确运行，不能直接推出组合后的系统正确。课堂还提到 α、β 测试作为验收相关的测试形式。

### 4. 软件为什么需要持续维护（69:00—76:30）

> **🟠 经常考／曾考过｜01:11:54｜软件维护：纠错、适应、增强**
> 口头提示（转写摘录）：“经常会考到”。

软件交付后仍会不断变化。课堂反复强调三类原因：

| 类型 | 核心含义 | 例子 |
|---|---|---|
| Correct：纠错 | 修复使用过程中暴露的缺陷 | 某种特殊购物或退款路径出现错误 |
| Adapt：适应 | 适应运行环境的变化 | 操作系统、数据库、网络或平台升级 |
| Enhance：增强 | 满足新的业务需求或改进功能 | 税务规则改变后调整业务处理 |

复杂系统存在大量输入组合、执行路径和交互场景，难以在交付前穷尽验证。软件已经通过测试，并不意味着以后不会暴露缺陷。

维护贯穿交付后的生命周期，可能消耗大量时间和资源。因此工程活动必须考虑系统能否被理解、修改和长期支持。

### 5. 过程、方法与工具（76:30—83:00）

- **过程（Process）**：组织开发活动，明确活动如何衔接。
- **方法（Methods）**：完成活动的具体技术，例如需求建模方法、等价类测试和边界值测试。
- **工具（Tools）**：支持或自动化这些方法，例如建模工具和测试工具。

三者配合的目标是更容易、更快速、以更合理的成本开发并维护高质量软件。工具提高效率，需要与合适的方法和过程结合。

### 6. 软件工程仍需解决的五类问题（83:00—134:28）

软件既是产品，也承担信息处理、存储、传输以及支撑其他产品交付的作用。它越广泛地融入业务，开发和维护中的问题就越重要。

| 问题 | 课堂讨论的应对思路 |
|---|---|
| 为什么开发周期长？ | 分阶段交付可用功能，通过增量与迭代缩短用户等待首次可用版本的时间 |
| 为什么开发成本高？ | 标准类库、构件和既有成果复用；用大模型辅助部分开发工作 |
| 为什么交付前难以发现所有错误？ | 复杂路径与交互难以穷尽，需要测试并重点验证主要业务场景 |
| 为什么维护耗费大量时间和精力？ | 软件持续纠错、适应、增强；利用运行数据辅助故障检测和处理 |
| 为什么进度难以准确度量？ | 估算工作量、制定计划并跟踪执行，仍需应对实际偏差 |

#### 6.1 复用与增量交付

酒店管理系统等同类应用可能具有大量共性功能。将共性能力整理为标准类库，可以减少重复开发。复用需要识别适用范围，并处理当前项目的差异。

增量交付先提供基本功能，再逐步增加能力，使用户更早使用系统。它缓解长时间等待的问题，但不会自动消除复杂性、成本和质量风险。

#### 6.2 智能运维与可观测数据

课堂以生产线检测系统为例：系统故障可能影响整条生产线，因此需要及时发现、定位并处理问题。运行数据包括：

- 日志（Logs）：记录运行事件与执行情况。
- 指标（Metrics）：反映系统运行状态的数值数据。
- 调用链（Traces）：反映方法或服务之间的调用关系。

这些数据可用于故障检测、分析和预测；结合人工智能的方法属于智能运维（AIOps）的研究方向。可记录、可分析的运行信息，是维护工作的基础。

#### 6.3 工作量、成本与进度

工作量可以用人月表示，估算时可参考类似项目和不同阶段的任务。课堂举例：某阶段需要 3 人月，每人月成本 5 万元，则估算成本为 15 万元。

工作量估算为人员安排和计划制定提供依据，之后仍要跟踪实际执行。人月是工作量单位，不能据此保证增加人员就能按比例缩短日历工期。

### 7. 软件的三个组成部分（134:28—147:30）

**软件 = 程序 + 数据结构 + 描述性信息。**

| 组成 | 含义 | 例子 |
|---|---|---|
| 程序／指令 | 执行时提供所要求的特性、功能和性能 | 业务处理、身份验证等实现 |
| 数据结构 | 使程序能够适当地操作信息 | 数组、链表、树等组织形式 |
| 描述性信息／文档 | 描述系统、开发成果以及操作使用方式 | 需求规约、设计文档、测试用例、项目计划 |

课堂将安全性等特性与非功能要求联系起来，并特别强调性能。性能属于非功能质量要求，但因其对实际使用的重要性而被单独突出。

数据需要以适当结构组织，程序才能有效处理。文档则保存需求、设计和验证的依据；若多年后需要维护一个系统，只剩代码会显著增加理解和定位问题的困难。

开发过程中产生的需求规约、分析规约、设计说明和测试资料等，可以统称为工作产品（Work Products）。

### 8. 硬件与软件的故障率曲线（147:30—154:08）

#### 8.1 硬件：浴缸曲线

横轴为时间，纵轴为故障率。早期可能因设计、制造缺陷而具有较高故障率；问题逐步处理后进入相对稳定阶段；使用后期因磨损、老化等原因，故障率再次上升。某些硬件故障可以通过替换部件修复。

#### 8.2 软件：变更与副作用

> **🔴 必考／明确会考｜02:32:33｜软件变更与故障率曲线**
> 口头提示（转写摘录）：“所以这个，这个考试会考到了啊”。

软件没有硬件式的物理磨损。理想情况下，原有缺陷修复后，故障率下降并趋于稳定。

实际软件不断因纠错、适应和增强而修改。修改可能引入新的缺陷或影响其他部分，导致故障率暂时升高；修复后下降，再次修改又可能出现新的波动。反复变更及其副作用可能使软件逐渐劣化，增加维护困难。

**区分：硬件后期故障增加与物理磨损有关；软件的劣化与变更带来的缺陷、复杂性等有关。** “软件不会物理磨损”不等于“软件永远不需要维护”。

### 9. 自测题与答题要点

1. **为什么会写代码不等于能完成大型软件项目？** 还需需求、建模、设计、协作、验证、交付与维护；程序只是软件的组成之一。
2. **需求分析与设计有何区别？** 分析理解要解决的问题和系统要求，设计决定实现结构与细节。
3. **为什么单元测试通过后仍需要集成测试？** 局部正确不能保证接口、数据交换和组合行为正确。
4. **数据库升级与税务规则变化分别属于什么变更？** 前者主要属于适应性修改，后者主要属于业务增强或调整。
5. **为什么软件交付后仍需保留文档？** 文档保存需求与设计依据，支持使用、问题定位及后续修改。
6. **软件故障率为什么可能在修改后上升？** 修改可能引入缺陷并对其他部分产生副作用。
7. **过程、方法、工具分别回答什么问题？** 活动如何组织、任务怎样完成、用什么支持任务。
8. **如何解释五类开发问题？** 围绕周期、成本、缺陷、维护、进度展开，并能为每项给出课堂案例或应对思路。
