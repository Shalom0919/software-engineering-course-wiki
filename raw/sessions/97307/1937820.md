### 1. 从工程化到过程框架（00:00—22:30）

软件工程通过组织过程、采用方法和工具，支持有质量要求的软件开发。课堂的逻辑主线是：**工程化 → 过程化 → 过程框架 → 开发活动与管理活动配合**。

过程可以逐层分解：

| 层次 | 英文 | 含义 |
|---|---|---|
| 过程 | Process | 组织完整的软件工作 |
| 活动 | Activity | 面向某个较大目标的一组工作，如需求分析 |
| 动作 | Action | 活动中的具体工作，如数据建模、功能建模 |
| 任务 | Task | 在当前管理粒度下可执行、可跟踪的具体任务 |

一个活动包含一个或多个动作，一个动作包含一个或多个任务。分解粒度随项目调整；关键是明确职责、成果及工作之间的联系。

#### 1.1 两个相互配合的维度

**框架活动（Framework Activities）**构成开发主线，例如需求获取、需求分析、设计、编码、测试、交付和维护。

**伞状活动（Umbrella Activities，也称保护性活动）**贯穿开发过程，承担计划、跟踪、质量保证、风险控制等职责。课堂把它概括为管理维度，用来保证开发活动及其成果的质量。

只完成需求、设计、代码等开发工作，仍需要回答：进度是否符合计划？成果是否遵守规范？风险是否受到控制？变更是否有记录？这些问题由伞状活动持续支持。

#### 1.2 教材与课堂划分的对应关系

| 教材通用框架 | 课堂展开 |
|---|---|
| Communication：沟通 | 需求获取，以及对需求的分析和理解 |
| Planning：策划 | 课堂将它重点放入管理维度讲解 |
| Modeling：建模 | 概要／架构设计和构件级详细设计等建模工作 |
| Construction：构建 | 编码、单元测试、集成测试、系统测试、验收相关测试 |
| Deployment：部署 | 发布、交付、支持与维护 |

教材明确列出五项框架活动；老师在解释开发维度时，将策划归入管理工作，并把其他活动展开得更细。复习时应分别识别两种组织方式。

### 2. 计划、跟踪与控制（22:30—30:48）

项目管理需要把活动分解为可安排的动作和任务，记录负责人、预计开始与结束时间、完成情况及依赖关系。课堂演示项目管理工具，并要求课程项目也开展这类管理。

以需求工作为例，可以安排需求收集、形成初稿、评审讨论、修改和确认。任务可以并行，也可能需要等待前置成果。

课堂提到四类任务关系：完成—开始（FS）、开始—开始（SS）、完成—完成（FF）、开始—完成（SF）。设置关系是为了表达真实约束，不能把所有任务都随意排成独立工作。

跟踪比较计划与实际；控制则根据偏差采取措施。记录“完成了多少”之后，还要分析延期或工作量增加的原因。

### 3. 风险管理（30:48—57:30）

风险是可能发生、并对项目造成损失的不确定事件。大型软件项目可能面临人员流失、设备交付延误、技术或成本等风险。

#### 3.1 风险曝光度

> **🔴 必考／明确会考｜00:39:57｜风险曝光度：概率乘以损失**
> 口头提示（转写摘录）：“这个考试肯定要考到啊”。

风险曝光度（Risk Exposure）用于综合考虑发生概率和影响：

$$RE = P \times L$$

其中 $P$ 表示发生概率，$L$ 表示风险发生后的损失或采用统一尺度评估的影响。

课堂强调先计算、再排序，选择优先处理的风险。若损失采用等级评分，应在同一套评分尺度下比较；具体等级边界需要统一约定。

#### 3.2 识别—缓解—跟踪

> **🔴 必考／明确会考｜00:35:54｜风险识别与类似项目经验**
> 口头提示（转写摘录）：“这考试都会考”。

1. **识别风险**：利用类似项目经验、历史记录和团队讨论，列出候选风险，估计概率与影响。
2. **制定缓解措施**：按曝光度排序，针对重点风险安排具体措施。课堂以选取前五项为例。
3. **持续跟踪**：检查措施执行情况，重新估计曝光度并调整优先级。

“前五项”是课堂示例中的管理选择。动态更新重点风险，比固定保留一份初始清单更重要。

#### 3.3 人员流失案例

> **🟡 可能考｜00:44:40｜人员流失风险及缓解措施**
> 口头提示（转写摘录）：“但最近这考试可能会考到”。

| 缓解措施 | 作用 |
|---|---|
| 加强团队沟通与协作 | 改善团队关系和协作体验 |
| 改善福利待遇 | 降低离职倾向 |
| 让不同成员了解同一任务或岗位 | 分散知识，减少人员离开造成的影响 |

跟踪一段时间后，人员流失风险的曝光度可能下降，其他风险进入优先处理范围。风险管理因此是一项持续、动态的活动。

设备延期案例说明：关键设备晚到会影响上线安排，并增加团队等待期间的成本。风险分析需要把事件与项目后果联系起来。

### 4. 软件质量保证与技术评审（57:30—68:30）

#### 4.1 软件质量保证：SQA

Software Quality Assurance 关注开发活动是否遵循约定过程和质量要求。课堂尤其强调在工作产品形成过程中开展检查。

例如，编码时检查编码规范和详细设计的一致性；建模时检查符号、模型结构和表达是否合理。需求规约、分析模型、设计说明和代码都属于关注对象。

自动扫描、分析工具和 AI 可以辅助检查。业务逻辑、需求理解和设计判断仍需结合人员评估。

#### 4.2 技术评审：Technical Review

技术评审针对已经形成、可供检查的工作产品开展集中审查。课堂举例包括代码、需求规约和设计资料，并提到正式技术评审及小组评审。

代码评审可以检查实现逻辑、与详细设计的一致性、变量与接口定义。评审形成报告，开发者依据问题记录整改。

| 对比点 | 课堂对 SQA 的强调 | 课堂对技术评审的强调 |
|---|---|---|
| 切入时机 | 工作产品形成过程中持续检查 | 对已经形成的工作产品进行评审 |
| 主要问题 | 是否按规范和要求开展工作 | 当前成果是否存在技术问题 |
| 后续动作 | 及时纠偏 | 记录问题、提交报告、整改 |

该对比用于理解课堂的工作划分；质量保证与评审在实际质量体系中相互配合。

### 5. 度量：Measurement（68:30—73:30）

度量把过程、项目和工作产品的情况表达为可比较的数据，再据此分析和改进。

- **工作量例子**：计划 4 人月，实际 5 人月，偏差为 1 人月。需要进一步寻找根因，如估算偏差、需求变化或返工。
- **缺陷例子**：评审 50 页需求规约发现 25 个缺陷，再按严重程度分类，用于判断质量并安排整改。

度量包含指标定义、数据收集和分析。人数、人月与日历工期是不同概念；工作量增加 1 人月不能直接等同于延期 1 个月。

### 6. 软件配置管理：SCM（73:30—79:17）

Software Configuration Management 管理软件工作产品及其变化，课堂重点讨论分支、合并和发布配置。

#### 6.1 标准版与客户化分支

一家开发酒店软件的公司可以维护核心标准版，并为不同酒店建立客户化分支。分支中的通用改进经过评估后，还可以合并回核心版本。

配置管理需要清楚记录版本来源、变更内容以及不同版本之间的关系。

#### 6.2 发布版本是一个明确的组合

课堂以 A、B、C、D 四个程序为例：一次交付可能需要 A 1.1、B 1.3、C 1.0、D 1.1，而各模块最新版本可能不同。

发布工作需要锁定目标版本组合，保证可以重新取得相同的交付内容。将每个模块都取最新版，未必得到客户需要的版本。

### 7. 复用管理与工作产品准备（79:17—90:47）

#### 7.1 复用管理：Reusability Management

复用可以涉及需求、设计和代码等成果，课堂重点展开代码复用与标准类库建设。

已有代码需要整理和改进，使结构、变量定义及接口适合复用；通过重构（Refactoring）改善内部组织，再将适合复用的构件归入代码库。后续相似项目可以复用这些成果，减少重复开发。

复用管理需要定义哪些成果可以复用、复用标准是什么，以及如何保存、查找和使用。随意复制旧代码会把原有问题带入新项目。

#### 7.2 工作产品准备与生产

Work Product Preparation and Production 涉及模型、规约、文档、表格、测试资料、用户指南及维护指南等成果。

这些资料支持开发衔接、使用和维护。例如发生问题后，需要借助需求和设计资料理解系统，进行纠错、适应性修改或增强。

### 8. 过程适应与裁剪（90:47—133:30）

通用过程为项目提供框架。具体项目需要根据规模、已有资产、风险、团队和业务要求进行调整，即 Process Adaptation / Tailoring。

裁剪包括删除、简化、修改和增加活动。课堂以类似酒店项目为例：已有数据模型可以修改后使用，已有构件可以减少重复开发和验证工作。采用复用成果时，应判断使用条件和变更影响，据此确定需要保留的验证。

| 裁剪维度 | 需要决定的问题 |
|---|---|
| 活动、动作和任务的整体流程 | 顺序、依赖和并行关系如何安排 |
| 活动内部的动作 | 哪些需要保留、增加或简化 |
| 工作产品 | 需要哪些文档和模型，详细到什么程度 |
| 质量保证 | 检查方法、范围与频度如何安排 |
| 跟踪与控制 | 多久检查进度，怎样处理偏差 |
| 过程详细程度与严格性 | 各项工作的粒度和规范要求 |
| 利益相关方参与 | 客户、供应商等在哪些阶段参与 |
| 开发团队自主程度 | 团队能自行决定哪些技术与组织事项 |
| 团队组织与角色 | 角色如何分配，人员是否动态调配 |

裁剪的依据是项目需要。小项目和大项目可以采用不同强度的过程管理，同时保留必要的质量目标。

### 9. 软件工程实践的四步（133:30—164:53）

#### 9.1 理解问题：Understand the Problem

理解问题包括获取需求并进行分析建模，重点回答四组问题：

1. 谁是利益相关方（Stakeholders）？谁提出要求、谁使用系统、谁能够对关键问题作决定？
2. 还有哪些未知条件？从数据、功能和非功能要求检查遗漏。
3. 问题能否分解？将大系统分成较小、较容易理解的部分。
4. 能否用图形或模型表达？用明确的符号和关系帮助理解、沟通。

课堂以图书管理系统说明系统分解，并用交易需在规定秒数内完成说明性能需求。性能会受到算法、架构、数据库和网络等多方面因素影响，不能只在写代码时局部处理。

#### 9.2 制定方案：Plan a Solution

寻找类似项目、可复用成果和已经验证有效的模式（Patterns）；利用需求分析模型形成架构和详细设计；将复杂问题分解为可以实现的部分。

设计方案需要表达清楚，能够指导后续实现。图书管理系统的前后端、子系统及类的划分，就是通过结构化设计逐步细化方案的例子。

#### 9.3 执行方案：Carry Out the Plan

编码以设计为依据，特别是构件级／详细设计。应能沿着“需求 → 分析 → 概要设计 → 详细设计 → 代码”追踪实现来源。

检查方案是否满足客户要求，各组成部分是否正确，以及设计和代码是否经过评审。可追踪性支持定位遗漏、理解变更影响和检查实现依据。

#### 9.4 检查结果：Examine the Result

> **🟡 可能考｜02:41:11｜Error、Defect、Failure 的区别**
> 口头提示（转写摘录）：“这个简单讲下这考试可能会考上”。

制定测试策略、选择测试方法、设计并运行测试用例，将结果与数据、功能和非功能需求比较，并向相关利益方反馈。

课堂区分开发活动中的错误（Error）、缺陷（Defect）和运行时失效（Failure），强调分析或实现中的问题可能在运行时表现为系统失效。术语的具体定义需与课程 PPT 对照；不应把每一个错误都直接等同于已经发生的运行失败。

### 10. 自测题与答题要点

1. **框架活动与伞状活动有什么关系？** 前者组织开发主线，后者贯穿过程，提供管理和质量支持。
2. **为什么风险清单需要更新？** 概率、损失和缓解效果会变化，优先处理的风险随之改变。
3. **如何比较两项风险？** 在统一尺度下计算 $RE=P\times L$，结合项目情况决定优先级。
4. **SQA 和技术评审如何区分？** 课堂分别强调形成过程中的检查，以及对已形成工作产品的审查。
5. **项目管理工具应记录什么？** 任务、负责人、计划时间、依赖关系和实际进度。
6. **为何不能直接用所有模块的最新版发布？** 客户要求的是经过确认的版本组合，需要保持兼容性和可重现性。
