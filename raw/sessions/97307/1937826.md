### 1. 核心原则复习：从大问题分解到可实现任务（00:00—25:25）

软件工程实践将复杂问题逐步分解为能够分析、设计、实现和验证的工作。分解需要理解业务，并形成清晰的职责与接口。

#### 1.1 分而治之与模块粒度

课堂以图书馆系统说明分解过程：整体划分为前端与后端；前端可能包含移动端和 PC 端；后端继续划分为系统管理、图书管理、借阅管理、出版社管理等子系统；子系统由类协作完成，类再提供具体方法。

不同层次对应不同的粒度（Granularity）。系统、子系统、类和方法的规模逐级缩小，工作内容逐渐具体。接口负责连接各部分，使分解后的局部能力能够组合成整体功能。

研究问题也可以采用类似思路。故障检测先明确业务问题与可获得的数据，再讨论日志、指标、调用链的处理方法，最后确定分析模型与验证方式。

#### 1.2 抽象与一致性

抽象从某个视角保留问题的重要信息。旅行规划系统的用例图从用户角度呈现行程规划、开销管理、天气查询等能力；分析模型继续表达数据、功能和行为；设计模型进一步支持实现。

一致性要求后续工作使用前面的成果作为依据：设计应对应需求分析，代码应对应详细设计。需求调整后，应检查相关模型、接口和测试是否同步更新。

课堂展示旅行规划项目的两轮需求文档。第二轮增加或细化了智能推荐、预算与报表等内容，用来说明需求和模型会随讨论与反馈演进。

#### 1.3 信息转换、模式与技术探针

系统运行表现为输入经过处理形成输出。例如借书时，用户输入身份与借阅信息，前端传递请求，后端验证并处理，再返回结果。各模块之间通过约定的数据与接口协作。

遇到不熟悉的工作，可以查找已有模式、方法和经验。针对尚不确定的技术方案，XP 的 Spike Solution（技术探针）通过小规模原型先验证关键问题。

课堂以订单折扣算法举例：先实现可试验版本，观察小规模和大规模数据下的效率与结果，再逐步改进。来自不同角度的讨论帮助提出方案，原型试验帮助检验方案。

### 2. 沟通原则：把业务需要转化为共同理解（25:25—42:16）

需求分析之前，需要通过沟通获取用户目标、业务规则及约束。大型项目应识别相关利益相关者，让不同角色的需求得到表达；敏捷项目也需要把本轮选定故事说明清楚。

#### 2.1 十项沟通原则

| 原则 | 具体做法 |
|---|---|
| 倾听 Listen | 让业务人员说明实际工作、问题与目标，开发方认真理解 |
| 沟通前准备 | 了解领域术语、现有流程和相关系统，准备讨论问题 |
| 有人促进沟通 | 组织议题、推动讨论并帮助形成结论 |
| 优先直接交流 | 面对面或合适的实时交流方式便于澄清问题 |
| 记录信息与决定 | 保存讨论要点、共识、待确认事项和后续任务 |
| 争取协作 | 围绕共同目标解决分歧 |
| 保持聚焦并分解讨论 | 将复杂议题拆为相互关联的小问题 |
| 不清楚时画图 | 用关系、流程和场景图辅助表达 |
| 合理推进议题 | 已达成共识就继续；暂时无法决定或澄清的事项记录后再处理 |
| 协商追求双方受益 | 共同寻找可实现且有价值的方案 |

#### 2.2 领域准备案例

课堂介绍光学领域项目：团队在需求交流前查阅资料，了解业务背景和已有系统，再形成初步问题清单。领域准备使讨论能够进入实际业务细节，也帮助开发者判断哪些问题需要专家进一步解释。

软件团队需要把技术能力与领域理解结合起来。先弄清业务要解决什么，再选择实现方式，需求讨论才能形成可执行内容。

#### 2.3 分解讨论与图形表达

促销金额计算可以分成正常销售金额、不同促销规则和最终金额组合等问题。将复杂规则逐项讨论，有助于确定方法职责，也方便后续实现与测试。

旅行规划系统可以用图展示智能推荐、行程规划、预算、开销与报表之间的关系。图形让双方围绕明确对象讨论范围和联系，文字说明补充条件与细节。

#### 2.4 处理暂时不清楚的需求

对已经达成共识的内容，记录决定并继续推进。对暂时无法澄清的功能，保留问题和后续确认安排，在迭代反馈中进一步解决。

这与原型及增量交付相互配合：用户体验已有成果后，可能更容易说明尚不明确的需要。团队据此更新故事和后续计划。

### 3. 计划原则：范围、依据和持续调整（42:16—75:37）

计划把目标转化为任务、人员、时间和验证安排。计划的详略应足以指导执行，并随着新信息更新。

#### 3.1 十项计划原则

| 原则 | 实施要点 |
|---|---|
| 理解项目范围 | 明确本轮功能、非功能要求及系统边界 |
| 利益相关者参与 | 共同确认目标、约束与安排 |
| 计划是迭代的 | 随需求和实际进展修订 |
| 基于已知信息估算 | 使用历史项目、规模和生产率等依据 |
| 在计划中考虑风险 | 安排缓解措施及必要投入 |
| 实事求是 | 结合实际能力、资源和依赖制定安排 |
| 调整粒度 | 把过大的任务细分到可执行、可跟踪的程度 |
| 明确质量保障方式 | 安排评审、测试和阶段完成条件 |
| 说明如何容纳变更 | 记录变更并评估实施时机与影响 |
| 经常跟踪并调整 | 比较计划与实际，及时修订后续工作 |

#### 3.2 Scope 包括边界与外部接口

项目范围需要说明本轮交付哪些能力，以及与外部系统和硬件怎样交互。课堂用支付接口说明：外部平台提供接口约定，开发团队仍需明确输入输出、调用方式和本系统承担的工作。

范围清楚后，才能估算开发、集成与验证所需投入。接口依赖也是计划中的重要条件。

#### 3.3 三种规模估算思路

课堂介绍 FP、KLOC 和 UCP，用于理解如何从软件规模进一步估算工作量。

| 名称 | 含义 | 使用思路 |
|---|---|---|
| Function Point，FP | 功能点 | 从软件提供的功能衡量规模，再结合生产率估算投入 |
| KLOC | 千行代码 | 用代码规模配合估算关系推算投入 |
| Use Case Point，UCP | 用例点 | 从用例等因素衡量规模，再转换为工作量 |

**规模与工作量需要通过生产率联系。**FP 是规模单位，人时是劳动投入单位；将两者换算时，应写清采用的生产率和估算条件。

#### 3.4 课堂估算例题

> **🟡 可能考｜00:53:29｜功能点与工作量估算**
> 口头提示（转写摘录）：“考试可能会考到啊”。
>
> **⚪ 待核实｜00:58:13｜估算例题的补充提示**
> 口头提示（转写摘录）：“考试没考到二”。

假设项目规模估计为 500 FP，类似项目的需求获取工作占总投入的 10%，生产率按每 FP 需要 6 人时计算。

$$E = 500 \times 6 = 3000\ \mathrm{person\!\cdot\!hours}$$

$$E_{req} = 3000 \times 10\% = 300\ \mathrm{person\!\cdot\!hours}$$

解题时依次写清总规模、生产率、阶段比例与计算结果。这里的 10% 和 6 人时来自例题假设，实际估算应参考可比较项目的数据。

课堂还讨论按复杂度差异修正估算。若基准工作量为 $E_0$，经评估确定调整比例为 $r$，可表达为：

$$E_{adjusted}=E_0(1+r)$$

这种调整需要说明差异来自哪些功能、技术条件或资源约束。人时换算为日历工期时，还要考虑人数、工作安排和任务依赖。

#### 3.5 风险要进入任务与投入

课堂以需求沟通困难和成员可能离职为例说明风险对计划的影响。前者可能增加澄清需求的投入；后者需要安排其他成员参与、知识共享或交接，降低单人依赖。

可复用成果、熟悉的业务和明确的需求也会影响估算。计划应根据实际新增工作调整投入，并记录依据。

#### 3.6 粒度、里程碑与质量检查

> **🟠 经常考／曾考过｜01:05:02｜里程碑与活动、动作的完成条件**
> 口头提示（转写摘录）：“考考了好几次了”。
>
> **🔴 必考／明确会考｜01:08:58｜计划原则中的质量保证与里程碑**
> 口头提示（转写摘录）：“就这 find how to Impact 的就必须考”。

若最初把单元测试、集成测试和系统测试合成一项任务，执行时发现难以跟踪，就应细分。Activity、Action、Task 提供从粗到细的组织层次。

**里程碑标记阶段完成，评审和测试为完成提供依据。**课堂计划示例将活动末尾的里程碑设为零工作量标记；实际评审、修复和测试工作应在此前的任务中安排。

例如，需求获取结束时，需求规约经过评审、发现的问题得到处理，形成可交给后续分析的版本，再标记达到里程碑。代码阶段则需要相应测试结果支撑完成判断。

考核中的对应关系是：里程碑与“明确如何保证质量”这一计划原则相关。完成标记应反映真实工作状态。

#### 3.7 变更提出与实施安排

客户可以提出新的需求；团队需要评估何时实施。课堂的通常安排是记录本轮正在开发故事的变化，放到后续迭代处理，以保持当前工作的稳定；迫切变化则需要重新协调范围和计划。

计划跟踪要持续进行。课堂以每周检查完成比例和偏差为例，说明计划应随实际进展调整。

### 4. 建模分类与四份规约（75:37—83:50）

建模分为需求建模和设计建模。需求建模帮助理解系统应做什么，设计建模说明如何组织实现。

| 文档 | 主要内容 | 后续用途 |
|---|---|---|
| 需求规约 Requirements Specification | 需求文字、场景与用例说明 | 确认业务需要，支持分析 |
| 需求分析规约 Requirements Analysis Specification | 数据、功能与行为模型 | 明确对象、逻辑和动态关系，支持设计 |
| 概要设计规约 High-Level / Architectural Design Specification | 架构、数据库、接口及相关界面安排 | 组织构件与协作，支持详细设计 |
| 详细设计规约 Detailed / Component-Level Design Specification | 类、方法、算法、内部数据结构及处理细节 | 支持编码和单元验证 |

课堂把场景建模主要放在需求规约中，把数据、功能和行为模型放在需求分析规约中。用户界面设计结合概要设计组织；项目应保持各文档之间的对应关系。

XP 可以把分析和设计组织在紧凑的设计活动中。课程项目仍要求通过四份文档练习完整的工程衔接。

### 5. 敏捷建模原则（83:50—95:00；119:49—121:43）

模型帮助团队理解问题、分配职责、讨论方案并指导实现。其价值体现在能否支持后续开发和验证。

#### 5.1 十项原则

1. 围绕软件实现目标建模。
2. 采用满足需要的模型数量，保持轻量。
3. 以尽量简单的模型表达问题和软件。
4. 让模型便于修改。
5. 为每个模型说明明确用途。
6. 按当前系统特点调整模型。
7. 优先保证模型有用、表达准确。
8. 让表示法服务于成功沟通。
9. 对感觉不合理的模型继续检查，即使图面完整也要核对业务含义。
10. 尽早获取反馈。

统一表示法能减少理解成本。课堂以 UML 为例，强调它提供建模符号与表达方式；团队需要让模型表达清楚，并保留必要说明。

#### 5.2 旅行规划系统案例

用户管理、行程规划、开销管理和天气查询等功能可通过不同模型表达。用例图展示用户可完成的任务，文字描述补充前置条件、后置条件和基本流程。

功能模型进一步展示完成任务的处理过程，以及参与协作的对象。天气查询涉及用户、身份验证、请求处理和外部天气服务等环节，模型帮助解释它们如何配合。

模型的修改随迭代推进。已有图和文档应便于更新，让新需求能够反映到相关结构和流程中。

### 6. 需求建模：数据、功能与行为相互联系（121:43—146:30）

课堂用五项分析原则组织需求建模：表达并理解信息域，定义系统功能，表达事件引发的行为，分层细化模型，以及从问题本质逐步走向实现所需细节。

#### 6.1 数据建模：识别实体及关系

数据模型描述问题空间中的实体、属性和关系。旅行规划系统可以识别用户、预算、开销、旅行计划、天气和报表等对象，再分析它们的关联。

类图可以表达属性、操作、关联、多重性与继承。用户类的标识、姓名等属性体现系统需要处理的数据；报表类可以通过继承组织共享能力与具体差异。

课堂强调类图经过多轮修改逐渐完善。它既帮助理解业务结构，也为后续数据库设计和类的实现提供依据。

#### 6.2 功能建模具有多个层次

功能模型说明系统执行哪些处理，以及处理之间如何衔接。活动图或流程图可以表达不同粒度的逻辑：

- 系统层次：主要功能及总体流程。
- 子系统层次：一组相关功能的组织。
- 用例层次：完成某个用户任务所需的处理。
- 更细层次：参与类和方法的具体逻辑，在设计中继续细化。

一个用例通常需要一个或多个类协作实现。功能模型说明处理逻辑，数据模型提供参与处理的对象；两者共同支持职责和方法的确定。

随着粒度细化，图中的一个节点可能从“大功能”逐步变成某个具体操作。模型层次应与当前讨论的问题一致。

#### 6.3 行为建模：事件、状态与动作

行为模型关注动态变化。课堂介绍状态图（State Diagram）和时序图（Sequence Diagram）：前者表达状态及事件触发的转换，后者表达对象之间按时间展开的交互。

系统层次可以用打印机说明：空闲时收到打印请求，进入打印状态；打印过程中发生卡纸，进入异常状态并触发处理。状态、事件和处理动作共同解释系统怎样响应外部变化。

类层次可以用订单说明：订单具有不同状态，添加商品、计算金额、支付等操作需要结合状态与业务规则组织。状态变化帮助检查方法的职责、调用条件和执行顺序。

#### 6.4 从分析走向设计

数据、功能和行为模型分别回答“有哪些对象”“完成哪些处理”“如何响应事件”。它们共同构成理解系统的基础，并通过逐层细化进入设计。

分析模型应关注业务含义；后续设计把这些含义落实为架构、接口、类和方法。保持模型之间的一致性，能够帮助团队评估需求变更的影响。

### 7. 设计原则：从需求依据到独立构件（146:30—165:01）

#### 7.1 十项设计原则

| 原则 | 核心要求 |
|---|---|
| 可追溯到需求模型 | 每项设计能找到需求和分析依据 |
| 始终考虑系统架构 | 明确系统划分与整体协作 |
| 重视数据设计 | 同时设计数据组织和处理功能 |
| 谨慎设计内外接口 | 明确参数、类型、结果和交互约定 |
| 面向最终用户设计界面 | 围绕使用需要与易用性组织交互 |
| 构件具有功能独立性 | 类和方法承担明确职责 |
| 构件之间保持松耦合 | 减少不必要的依赖和信息传递 |
| 设计表示易于理解 | 图与说明能帮助团队理解实现安排 |
| 迭代开展设计 | 随新增认识与反馈逐步完善 |
| 设计建模兼容敏捷 | 在迭代中保留有用的设计依据 |

#### 7.2 架构与数据设计

概要设计关注软件架构、数据库及接口安排。前端与后端、不同子系统、系统与外部服务的关系清晰后，团队才能判断新增功能或缺陷修复会影响哪些部分。

数据设计包括数据库设计和内部数据结构设计。数据库组织需要持久保存的数据；详细设计还要选择算法和方法运行时使用的数组、链表、栈等结构。

课堂以实体关系到关系表的转换帮助理解数据库设计：一对多关系通常在“多”侧保存关联键，多对多关系通常通过关联表表达。具体约束需结合业务含义确定。

数据结构影响处理方式和算法实现。设计方法时，应同时明确数据怎样组织、读取和修改。

#### 7.3 内部接口与外部接口

内部接口包括方法、类、子系统和前后端之间的调用。接口设计要明确传入信息、类型和返回结果，让调用者与提供者按照相同约定协作。

外部接口包括支付平台、地图服务和硬件设备等。课堂以图书馆刷卡机举例说明，软件与硬件交互同样需要接口约定和验证。

#### 7.4 界面原型

课程项目采用原型方式设计界面。借助工具确定页面、颜色、跳转与基本交互，让用户和团队能够体验、讨论并修改设计。

界面原型服务于使用需要和易用性判断，并与系统功能及后续实现衔接。

#### 7.5 功能独立与松耦合

> **⚪ 待核实｜02:43:49｜功能独立与松耦合**
> 口头提示（转写摘录）：“输入耦合考试怎样考到二中”。

课堂把订单管理和支付处理分配给不同职责：订单类管理订单相关信息与操作，支付职责通过相应构件提供。添加商品、计算金额等方法也应有清晰的任务边界。

功能独立性关注一个构件承担什么；耦合关注构件之间怎样依赖。职责明确后，再用简洁接口连接各部分。

课堂用参数数量和参数结构说明松耦合：调用时传递完成任务所需的信息，避免让调用者依赖过多内部细节。参数简洁是降低依赖的一种做法，判断耦合还需要结合数据含义与整体接口关系。

### 8. 自测题

1. 课程项目的四份规约是什么？——需求、需求分析、概要设计和详细设计规约。
2. 沟通前为何需要领域准备？——帮助理解业务术语、流程与问题，使讨论能够深入实际需求。
3. 无法当场澄清的需求怎样处理？——记录疑问与后续安排，结合原型或迭代反馈继续澄清。
4. 项目范围除了功能还包括什么？——非功能要求、系统边界及外部软件和硬件接口。
5. 500 FP、每 FP 6 人时、需求阶段占 10%，该阶段估算多少？——300 人时。
6. 成员离职风险如何进入计划？——安排知识共享、交接或共同参与，并计入相关任务和投入。
7. 里程碑与评审测试有何关系？——里程碑标记完成，评审、修复和测试提供完成依据。
8. 建模分为哪两大类？——需求建模与设计建模。
9. 数据、功能和行为模型分别表达什么？——对象与关系、处理逻辑、事件与动态响应。
10. 状态图与时序图各关注什么？——状态转换，以及对象之间按时间展开的交互。
11. 数据设计包含哪些内容？——数据库设计和实现所需的内部数据结构设计。
12. 功能独立与松耦合如何配合？——先明确构件职责，再通过简洁接口减少不必要依赖。
